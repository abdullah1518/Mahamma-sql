 1. Introduction  
This document presents Phase 2 of the Mahamma project — the campus -centric freelance 
marketplace database introduced in Phase 1. Phase 2 covers the transition from the conceptual 
Entity -Relationship model to a fully implemented relational database in Postg reSQL, including 
all integrity constraints, derived -attribute logic, indexing strategy, and a populated set of sample 
data.  
During the implementation phase, we revisited and refined our original ER model based on a 
careful re -reading of the problem statement. Several gaps were identified — particularly around 
milestone tracking, skill -based matchmaking, and bidirectional review s — and have now been 
incorporated into the schema. The revised design is presented below.  
2. Revisions to the Conceptual Model  
Phase 1 delivered a solid foundation, but moving toward implementation revealed a number of 
refinements that strengthen the design and align it more closely with the stated objectives. The 
changes below are additive rather than destructive — the core entit ies (Student, Gig, Proposal, 
Contract, Review) remain intact.  
2.1 New Entity: Milestone  
The original ER model represented an entire contract by a single DeliveryDate, which 
contradicts the problem statement's emphasis on milestone tracking. A new weak -style entity 
Milestone has been added, owned by Contract through a one -to-many relationship.  Each 
milestone carries its own description, due date, partial amount, and lifecycle status.  
2.2 New Relationship: Gig requires Skill  
Skill was defined in Phase 1 but only loosely connected to Student. A gig now declares the skills 
it requires through a many -to-many relationship implemented as the gig_skill junction table. This 
unlocks freelancer matchmaking — a key feature of any freela nce platform.  
2.3 New Relationship: Student possesses Skill  
The 'possesses' relationship between Student and Skill is now formalized as a many -to-many 
relationship resolved by the student_skill junction table, including a proficiency_level attribute 
(Beginner / Intermediate / Advanced / Expert).  
2.4 Strengthened Review Entity  
Review now records both reviewer_id and reviewee_id, supporting bidirectional reviews (client 
↔ freelancer). A CHECK constraint enforces that reviewer_id ≠ reviewee_id, and a UNIQUE 
constraint on (contract_id, reviewer_id) prevents a single party from posting more than one 
review per contract.  
2.5 New Status Attributes  
A status attribute was added to Proposal (Pending / Accepted / Rejected / Withdrawn) so the 
bidding lifecycle can be tracked. Status fields on Gig, Contract, and Milestone were promoted to 
PostgreSQL ENUM types for type safety and storage efficiency.  
2.6 Derived Attribute: Student Rating  The rating column on Student is a derived attribute: it is automatically recalculated by a trigger 
function (update_student_rating) every time a review is inserted, updated, or deleted. The 
stored value is therefore always consistent with the underlying re view data, while remaining 
cheap to read at query time.

4. Logical Design — Relational Schema  
This section translates each entity and relationship into a relational table. Primary keys are 
underlined by convention; foreign keys reference the parent table in parentheses. All tables use 
SERIAL primary keys (PostgreSQL auto -increment) and snake_case c olumn naming.  
4.1 Schema Summary  
The database consists of nine tables organized into three logical groups:  
• Identity & Catalogue: student, skill, student_skill  
• Job Lifecycle: gig, gig_skill, proposal, contract, milestone  
• Reputation: review  
4.2 Custom ENUM Types  
PostgreSQL ENUM types are used in place of free -text VARCHAR for all status fields. This 
guarantees type safety at the database level and prevents subtle bugs (e.g., 'Completed' vs 
'completed' vs 'Complted') from corrupting status filters.  
• gig_status: Open, In Progress, Completed, Cancelled  
• proposal_status: Pending, Accepted, Rejected, Withdrawn  
• contract_status: Active, Completed, Cancelled, Disputed  
• milestone_status: Pending, In Progress, Submitted, Approved, Rejected  
• proficiency_level: Beginner, Intermediate, Advanced, Expert

6. Integrity Constraints  
Beyond primary and foreign keys, the schema enforces a number of CHECK constraints and 
UNIQUE constraints to protect data quality at the database layer:  
• Domain checks: score BETWEEN 1 AND 5; rating BETWEEN 0 AND 5; budget > 0; 
bid_amount > 0; agreed_amount > 0; estimated_time > 0; email LIKE '%@%.%'.  
• Business rules: deadline > posted_date; reviewer_id ≠ reviewee_id; one contract per 
proposal (UNIQUE on contract.proposal_id); one review per reviewer per contract 
(UNIQUE on (contract_id, reviewer_id)).  
• Referential actions: CASCADE on junction tables (student_skill, gig_skill) and on 
dependent records (milestone, review). RESTRICT on student references from gig and 
proposal, on the proposal → contract relationship, and on student references from 
review — preventing the silent loss of work history when a related record is deleted.  
7. Indexing Strategy  
PostgreSQL does not automatically index foreign -key columns. To keep JOIN performance 
acceptable as the dataset grows, explicit indexes have been added on every foreign key, on 
frequently filtered status columns (gig.status, proposal.status, contract.statu s), and on 
gig.posted_date for browsing the newest gigs. A partial index on gig(posted_date DESC) 
WHERE status = 'Open' accelerates the most common front -end query — listing all currently 
open gigs — while keeping the index size minimal.  
8. Triggers and Derived Logic  
8.1  update_student_rating()  
A row -level trigger on the review table fires AFTER INSERT, UPDATE, or DELETE. It 
recalculates the average score of all reviews received by the affected reviewee and writes the 
rounded result back to student.rating. UPDATE handlers correctly process both t he OLD and 
NEW reviewee_id, ensuring ratings remain consistent even when a review is reassigned.  
8.2  set_updated_at()  
A generic BEFORE UPDATE trigger function applied to the two tables that carry an updated_at 
column — student and gig. It sets updated_at = NOW() on every UPDATE, providing automatic 
auditing without requiring application -side bookkeeping. Defining the func tion once and 
attaching it to multiple tables keeps the logic DRY and the schema easy to maintain.  
9. Sample Data Strategy  
The seed.sql script populates each table with realistic sample data drawn from the KFUPM 
context — majors include ICS, COE, SWE, EE, and ME; emails follow the @kfupm.edu.sa 
pattern; skills span Programming, Design, Academic, and Engineering categories. Ins erts use 
JOIN -based lookups rather than hard -coded surrogate IDs, so the script remains correct on 
every re -run. The data is engineered to tell a coherent story:  
• 12 students with overlapping skill sets, several active as both clients and freelancers.  
• 12 skills across four categories (Programming, Design, Academic, Engineering).  
• 24 student –skill associations with proficiency levels.  
• 12 gigs with varied statuses (6 Open, 3 In Progress, 3 Completed).  
• 18 gig –skill associations declaring the skills required by each gig.  
• 15 proposals across multiple gigs, exercising every proposal_status value.  
• 6 contracts derived from Accepted proposals.  
• 13 milestones distributed across in -flight and completed contracts.  
• 6 reviews on Completed contracts; ratings are computed automatically by the trigger 
rather than hard -coded.  All inserts are wrapped in a single transaction (BEGIN … COMMIT), so the seed script either 
fully succeeds or rolls back cleanly — making it safe to run repeatedly during development.
